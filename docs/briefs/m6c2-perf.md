## The measurement problem, and what to do about it
`npm run perf` runs the real rAF loop in headless Chromium at 4x CPU throttle for 10 s and checks `workMeanMs` ≤ 10 and `workP95Ms` ≤ 16.6 (work = sim + scene update + render submit + UI + audio inside the rAF callback; DECISIONS 11). Recent runs on the city: mean 5.5–7.6 ms, p95 14–22 ms. Three things make that number poor to steer by:
- Headless Chromium rasterises in software, so the run gets only about 10 frames a second: roughly 100 frames in 10 s, and each frame carries up to four catch-up sim steps. p95 is then the fifth-worst frame.
- The machine is shared: other agents' test runs change the result by several milliseconds.
- The built-in `perf` route teleports between spawn zones, and every teleport builds nine chunks at once.
So first make the measurement trustworthy, then optimise:
1. Add a breakdown: in `main.ts` time each part of the frame separately (sim steps and how many; game reducers; view update split into vehicles, world streaming, skater/strap/aim, markers, chalk, camera; render submit; UI; audio) into fixed-size numeric buffers (no allocation), expose them through the test hook's `stats()` as an optional `parts` record of arrays, and print mean and p95 per part in `tests/perf/run.mjs`. Keep the overhead of the timing itself negligible (one `performance.now()` per boundary).
2. Make the `perf` route representative: a continuous run that a player could do: start at the summit spawn, ride down the spine carving and hopping, hold near rides so it hitches and slings, and when it reaches the docks go back to the top once (one teleport per descent, not one every few seconds). It must work on any world (the slice has no summit: fall back to the world's spawn).
3. Report work per sim step as well as per frame, and the number of sim steps per frame, so a frame that carries four catch-up steps is not mistaken for a slow frame. Add budgets for the per-step cost: game step (sim + reducers) mean ≤ 0.6 ms and p95 ≤ 1.5 ms at 4x throttle; and for a frame with exactly one sim step: mean ≤ 6 ms, p95 ≤ 10 ms at 4x throttle. Keep the existing two budgets as they are.
4. Measure when the machine is as quiet as you can get it (check `uptime`; if the load average is above about 1.5 from other work, take the best of three runs and say so), and always report load alongside numbers.

## Then find and fix the cost
Likely suspects, in the order I would check them (verify before believing any of this):
- `vehicleAt` is called for every vehicle of every line by: `tryHitch` (while armed), `collideVehicles` (every ground/air tick), the vehicle view (every frame), `audioView` (every sixth frame), the UI stop board and destination board, markers, and reducers (progress while hitched, conductors, onboarding later). Each call does two binary searches on paths that are now resampled every half metre (thousands of points). There are 16 lines and about 35 vehicles. Options: reject by line bounding box before calling (most lines are far away); cache each vehicle's state per tick in one shared table filled lazily; make `pathAt` remember the last segment (vehicles move forward a little each tick).
- Up to four catch-up sim steps per frame at 10 fps: each runs every reducer. Check the reducers' `step` for scans over all zones/lines/vehicles each tick (errand offers, conductor starts, secrets zone checks): they should early-out by distance or run every N ticks.

- World streaming: chunk builds are capped at 2 ms a frame (DECISIONS 48); check the cap is honoured under throttle (a single build piece must not exceed it by much) and that nothing rebuilds while standing still.
- Markers, chalk view, skater pose swaps, the strap and aim meshes: allocation or geometry rebuilds per frame.
- Audio `update`: scheduling work per frame, node creation bursts.
- `renderer.info`, uniforms and the post pass: draw calls are low (20–26), so this is unlikely to be the main-thread cost; confirm with the breakdown.
Fix what the breakdown shows, biggest first. No visual change, no behaviour change. For anything in the sim, results must be bit-identical.
